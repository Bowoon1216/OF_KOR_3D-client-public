# 상용망 회선 성능 — 업로드/다운로드 비대칭 측정 보고

**측정일** 2026-08-13 (KST 00:06–00:42) · loopback 2026-08-14 21:56
**위치** 가정 · **회선** LG U+ FTTH, Wi-Fi
**서버** AWS EC2 t3.medium, ap-northeast-2 (서울) · **타겟** `https://AWS_HOST_REDACTED`

## 1. 요약

3D 에셋의 실제 전송 시간을 측정한 결과, 이 회선은 **다운로드가 업로드보다 약 4.9배 빠르다.**
두 방향 모두 회선 용량에 도달했고 서버 상한은 회선의 4~5배로 실측됐으므로, 이 값은 서버나
파일 특성이 아니라 **회선 자체의 성능**이다.

| 방향 | 최고 처리량 | 대표 조건 | 1MB 전송 시간 |
|---|---:|---|---:|
| **다운로드** | **341.38 Mbps** | 339.23MB 단일 스트림 | 23.6 ms/MB |
| **업로드** | **69.60 Mbps** | 32.90MB IFC | 114.7 ms/MB |
| **비대칭비** | **4.91 : 1** | | 4.86 : 1 |

동시 다운로드를 합산하면 최대 **393.26 Mbps** 까지 나오므로, 합계 기준 비대칭은 **5.65 : 1** 이다.

**서비스 관점의 함의**: 건축가가 32.9MB IFC 를 올리는 데 **3.77초**, 그 결과물(36.6MB GLB)을
다른 참가자가 받는 데 **0.96초** 다. 체감 지연은 업로드 쪽에서 발생하며, 참가자 수를 늘려도
업로드 시간은 줄지 않는다.

## 2. 측정 방법

계획서 `ASSET_TRANSFER_TEST_PLAN.md` 를 따랐다. 요지만 적는다.

| 항목 | 내용 |
|---|---|
| 대상 | 실제 백엔드 (`POST /api/assets/ifc`, `GET /static/assets/…`). 측정 전용 서버 아님 |
| 다운로드 파일 | hoist 20단 적층 씬의 3개 압축 변형본 (339.23 / 36.64 / 13.60 MB) |
| 업로드 파일 | BIM 원본 IFC 3종 (32.90 / 19.90 / 4.93 MB) — 실제 사용자가 올리는 형식 |
| 반복 | 조건마다 워밍업 1라운드를 버리고 R회 반복. 총 **660 샘플** (상용 590 + loopback 70) |
| 캐시 | 매 요청 `?t={ns}` + 서버 `Cache-Control: no-store` |
| 오염 제거 | 라운드 전후로 AWS ENA 스로틀 카운터를 대조. 증가한 라운드는 집계 제외 |
| 변환 분리 | 업로드는 `?convert=false` 로 IFC→GLB 변환을 제외. 전송 시간만 측정 |

측정 도구는 `scripts/measure.py` (CLI, 권위 데이터)와 `src/measure/transferHarness.ts`
(브라우저, 보조)다. 두 하네스가 같은 JSON 스키마로 출력하며 스키마 검사를 통과했다.

## 3. 다운로드

| 변형 | 크기 | C | n | p50 (ms) | p95 (ms) | 처리량 중앙값 (Mbps) | 합계 (Mbps) | CV |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| raw | 339.23 MB | 1 | 10 | 8,011.6 | — | **341.38** | 341.38 | 0.033 |
| meshopt | 36.64 MB | 1 | 30 | 963.2 | 1,226.9 | 304.63 | 304.63 | 0.106 |
| meshopt | 36.64 MB | 3 | 60 | 2,522.7 | 3,319.4 | 115.12 | **345.35** | 0.240 |
| meshopt | 36.64 MB | 10 | 200 | 7,445.1 | 8,996.3 | 39.33 | **393.26** | 0.413 |
| draco | 13.60 MB | 1 | 30 | 414.2 | 619.6 | 263.05 | 263.05 | 0.155 |
| draco | 13.60 MB | 10 | 200 | 2,920.5 | 3,585.1 | 37.15 | 371.53 | 0.415 |

`C` = 동시 스트림 수. `CV = stddev / mean` (처리량 변동성). **CV 를 "지터" 로 부르지 않는다** —
지터는 RTT 연속 샘플 간 변화량으로 동기화 측정에서 쓰는 별개 지표다.
`n < 30` 조건은 p95 를 산출하지 않았다 (표본 부족).

### 회선 용량에 도달했다는 근거

동시성을 1 → 3 → 10 으로 **10배** 올려도 합계 처리량이 341 → 345 → 393 Mbps 에서 멈춘다.
스트림당 처리량이 동시성에 거의 정확히 반비례한다(304.63 → 115.12 → 39.33). 고정된 용량을
나눠 쓰는 형태이며, 서버가 여유가 없어서 나는 현상이 아니다.

단일 스트림 341.38 Mbps 는 같은 세션의 speedtest 실측(227.12 Mbps)의 **150%** 다. 즉
speedtest 가 회선을 과소평가했고, 실제 용량은 340~390 Mbps 대에 있다.


### 서버 상한은 회선의 4~5배 — loopback 직접 측정 (2026-08-14)

위 논거는 간접 근거다. 서버가 자기 자신을 부르게 해(loopback) 네트워크를 뺀 상한을 직접
쟀다. 같은 공개 호스트명·같은 TLS·같은 nginx 블록을 타되 주소만 `127.0.0.1` 로 꺾었고,
ENA 스로틀 카운터가 움직이지 않아 트래픽이 ENI 를 거치지 않았음을 확인했다. n=70, 오염 0.

| 변형 | loopback p50 | loopback 처리량 | 상용망 처리량 | 배수 |
|---|---:|---:|---:|---:|
| raw (339.23MB) | 1,600.3 ms | **1,696.31 Mbps** | 341.38 | **4.97×** |
| meshopt (36.64MB) | 214.8 ms | **1,377.81 Mbps** | 304.63 | **4.52×** |
| draco (13.60MB) | 108.7 ms | **1,016.38 Mbps** | 263.05 | **3.86×** |

서버 상한은 **1.02~1.70 Gbps** 로 집 회선의 4~6배다. 세 변형 모두 계획서가 정한 보고
기준(3배)을 넘으므로 **"서버가 병목이 아니다" 는 간접 근거가 직접 증거로 확인됐다.**
작은 파일일수록 배수가 낮아지는 것(4.97 → 3.86)은 고정 비용 비중이 커지기 때문이다.

이 값은 "상한" 이 아니라 **"상한의 하한 근사"** 다. 2 vCPU 에서 부하 생성기와 서버가 CPU 를
나눠 쓰므로(그래서 loopback 은 C=1 로만 잰다) 실제 상한은 더 높다. 정적 파일을 내는 것은
nginx 가 아니라 FastAPI `StaticFiles` 이므로 "nginx 상한" 이라고 부르지 않는다.

## 4. 업로드

| 파일 | 크기 | n | p50 (ms) | 처리량 중앙값 (Mbps) | CV | 1MB당 | 서버 작업 | 서버 비중 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| hoist | 32.90 MB | 20 | 3,773.7 | **69.60** | 0.054 | 114.7 ms | 114.4 ms | 3.0% |
| boomlift | 19.90 MB | 20 | 2,371.5 | 65.99 | 0.110 | 119.1 ms | 70.7 ms | 3.0% |
| rooflight | 4.93 MB | 20 | 643.2 | 58.84 | 0.139 | 130.5 ms | 22.1 ms | 3.4% |

`n = 20` 이므로 p95 는 산출하지 않았다.

업로드 최고 69.60 Mbps 는 speedtest 상향 실측(71.12 Mbps)의 **98%** 다. 다운로드와 마찬가지로
회선 한계에 도달했다.

### 서버 처리 시간은 3% 다

서버가 `Server-Timing` 헤더로 구간을 돌려준다. 이를 분해하면:

| 구간 | hoist (32.90MB) | 비중 |
|---|---:|---:|
| `recv` (본문 수신) | 3,602.7 ms | 95.5% |
| `store` + `db` (서버 작업) | 114.4 ms | **3.0%** |
| 전체 응답 시간 | 3,773.7 ms | 100% |

**`recv` 는 서버 처리 시간이 아니라 네트워크 시간이다.** nginx 가
`proxy_request_buffering off` 로 본문을 흘려보내므로 서버의 multipart 파싱이 클라이언트
바이트 도착 속도에 묶인다. 따라서:

```
서버 작업     = store + db           = 114.4 ms
네트워크 시간 = 전체 - 서버 작업       = 3,659.3 ms
```

`recv` 를 추가로 빼면 네트워크 시간이 **56.6 ms** — 실제(3,659.3 ms)의 **1.5%** — 로 나와
회선 성능을 실제보다 65배 좋게 잡는다. **9월 KOREN 비교 시 이 이중 차감을 하면 개선폭을
과소평가한다.**

업로드가 느린 것은 회선 상향 대역 때문이며, 서버 성능과는 무관하다.

## 5. 비대칭의 구조

| 지표 | 다운로드 | 업로드 | 비율 |
|---|---:|---:|---:|
| 최고 처리량 (단일 스트림) | 341.38 Mbps | 69.60 Mbps | **4.91 : 1** |
| 최고 처리량 (합계) | 393.26 Mbps | — | 5.65 : 1 |
| 1MB 전송 시간 | 23.6 ms | 114.7 ms | 4.86 : 1 |
| speedtest 대비 실측 | 150% | 98% | — |
| 동시성 확장 | 합계 포화 (341→393) | 미측정 (C=1만) | — |

업로드는 동시성 스윕을 하지 않았다. 가정용 회선의 상향 대역이 낮아 C 를 올리면 회선만
포화되기 때문이다(계획서 §3.2). 다운로드 결과로 보아 업로드도 합계가 70 Mbps 대에서
포화할 것으로 보이나 **이는 측정하지 않은 추정이다.**

### 전송 외 고정 비용

파일이 작아지면 처리량이 떨어진다 (raw 341 → meshopt 305 → draco 263 Mbps). 크기에
정비례한다면 나오지 않아야 하는 차이다.

| 변형 | 크기 비례 예상 | 실측 p50 | 초과 |
|---|---:|---:|---:|
| meshopt (36.64MB) | 865.3 ms | 963.2 ms | **+97.9 ms** |
| draco (13.60MB) | 321.1 ms | 414.2 ms | **+93.1 ms** |

초과분이 파일 크기와 무관하게 93~98 ms 로 일정하다 — 요청당 고정 비용이다. 그 내역:

| 성분 | 값 | 근거 |
|---|---:|---|
| DNS + TCP + TLS 핸드셰이크 | 25.0 ms | CLI `time_pretransfer` 중앙값 |
| 서버 응답 시작 | 8.1 ms | 브라우저 Performance API (커넥션 재사용 상태) |
| 나머지 | 약 60 ms | **추정** — TCP slow-start 의 congestion window 상승 구간 |

CLI TTFB 34.4 ms 중 **25.0 ms(72%)가 연결 수립 비용**이고 서버가 응답을 시작하는 데 쓰는
시간은 8~9 ms 다. 브라우저가 커넥션을 재사용한 상태에서 독립적으로 측정한 순수 서버 응답
8.1 ms 가 CLI 의 잔차와 일치한다 — 두 하네스가 서버 구간에서 교차 검증됐다.

마지막 약 60 ms 는 slow-start 로 해석되나 **측정으로 확인한 것이 아니라 추정이다.**

**실무적 의미**: 작은 파일을 여러 번 받는 것보다 한 번에 받는 것이 유리하다. 파일당
약 95 ms 의 고정 비용이 붙는다.

## 6. 측정의 한계

수치를 인용할 때 함께 밝혀야 하는 항목들이다.

**Wi-Fi 노이즈가 포함되어 있다.** 공유기까지의 RTT 가 avg 7.243 ms / **mdev 11.61 ms** /
최대 80.24 ms (손실 0%)였다. mdev 가 avg 보다 크다는 것은 간헐적 스파이크가 있다는 뜻이며,
이 노이즈가 위 모든 측정값에 들어 있다. 유선으로 재면 CV 가 낮아질 것이다.

**서버 RTT 를 ping 으로 측정하지 못했다.** AWS 가 ICMP 를 차단해 30발 전부 손실됐다.
traceroute 도 9홉까지만 응답하고 목적지에 도달하지 못했다. 대용으로 다운로드 TTFB
중앙값 39.2 ms 를 기재했다 — 왕복 1회와 서버 응답 시작을 포함하므로 RTT 의 상한 근사다.

**서버 상한은 하한 근사다.** loopback 으로 1.02~1.70 Gbps 를 실측했으나, 2 vCPU 에서 부하
생성기와 서버가 CPU 를 나눠 쓰므로 이 값은 상한의 **하한 근사**다. 실제 상한은 더 높다.
회선이 10 Gbps 급으로 바뀌면 이 값으로는 서버가 받아줄지 판단할 수 없고, 부하 생성기를
분리한 별도 측정이 필요하다.

**tmpfs 가 아니라 EBS 에서 서빙됐다.** 계획서 §1 은 tmpfs 서빙을 전제하지만, 측정이 실제로
때린 경로는 `/static/assets/a_*` (EBS gp3) 였다(서버 nginx 접근 로그 확인). 이 조건에서도
회선 용량을 다 채웠으므로 결론은 바뀌지 않는다. 정적 파일을 내는 것은 nginx 가 아니라
FastAPI `StaticFiles` (uvicorn) 이며, nginx 는 `proxy_pass` 만 한다.

**단일 지점·단일 시각이다.** 가정 Wi-Fi, 자정 무렵 1회 측정이다. 시간대·위치를 바꾸면
값이 달라진다. 8월 측정의 목적은 도구 검증과 수치 감각 확보이며, 발표용 비교 데이터는
9월에 같은 장소·같은 기기·같은 시간에 AWS 와 KOREN 을 동시 측정해 얻는다.

**업로드 p95 가 없다.** R=20 이라 표본이 30 미만이어서 p95 를 산출하지 않았다. 필요하면
R=30 이상으로 재측정한다. `?convert=false` 때문에 변환 대기가 없으므로 추가 비용은
전송 시간뿐이다.

## 7. 9월 KOREN 비교를 위한 기준선

이 측정값이 8월 AWS 기준선이다. 9월에는 같은 스크립트에 `--target` 만 바꿔 실행한다.

| 항목 | 8월 AWS (상용망) |
|---|---:|
| 다운로드 최고 (단일) | 341.38 Mbps |
| 다운로드 최고 (합계) | 393.26 Mbps |
| 업로드 최고 | 69.60 Mbps |
| 서버 상한 (loopback, 하한 근사) | 1,016 – 1,696 Mbps |
| 요청당 고정 비용 | 약 95 ms (핸드셰이크 25 + 서버 8 + 기타 62) |
| TTFB 중앙값 | 39.2 ms |
| 비대칭비 | 4.91 : 1 |

비교 시 반드시 지킬 것:

1. **같은 파일을 쓴다.** 씬을 재생성하지 않는다. sha256 이 기록되어 있다
   (`results/download_targets_commercial.json`)
2. **`recv` 를 빼지 않는다.** 서버 작업은 `store + db` 뿐이다 (§4)
3. **KOREN 처리량을 서버 상한과 대조한다.** 서버 상한은 1.02~1.70 Gbps 로 실측됐다.
   KOREN 측정치가 이 구간에 근접하면 회선이 아니라 서버에 걸린 것이므로 개선폭이
   과소평가된다 — 그때는 loopback 을 다시 재고 부하 생성기를 분리한다
4. **loopback 도 같은 `a_*` 경로를 잰다.** 매체가 다른 두 값으로 비율을 내면 3배 판정이
   오염된다
5. **스로틀 카운터를 대조한다.** t3 계열은 네트워크가 버스터블이며, 크레딧이 마른 구간의
   측정값은 회선이 아니라 AWS 정책을 잰 것이다
