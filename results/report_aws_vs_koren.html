KOREN 을 써야 할 이유는 속도가 아니라 인원이다

03KOREN 이 이기는 지점 — 인원

서버 상한은 loopback(서버가 자기 자신을 부름)으로 쟀다. 1인 전송에서는 클라이언트 회선이 먼저 막혀 이 상한이 드러나지 않는다. 참가자가 늘면 상한이 먼저 걸린다.

갈리는 지점은 AWS 4.6명 / KOREN 9.2명이다 (상한 ÷ 300 Mbps). 그 아래에서는 두 서버가 같고, 그 위에서는 서버 상한이 참가자당 속도를 정한다. 10인 방에서 도면 교체가 AWS 2.13초, KOREN 1.06초다.

이 표는 산출값이다. loopback 상한(실측)을 인원으로 나눈 것이며, 실제 다중 클라이언트 측정으로 확인하지 않았다 — §05 참조.

한 달에 546개 방을 넘으면 과금이 시작된다. 원본 raw(339.23MB)를 그대로 배포하면 295회다. 계획서 §11 도 "egress 60GB 초과" 를 중단·보고 조건으로 두고 있으니 프로젝트가 이미 인식한 제약이다. 측정 한 번이 무료 한도의 20% 를 먹었다.

이것은 속도 논거가 아니라 경제성 논거다. 그러나 "왜 KOREN 인가" 에 대한 답으로는 정당하고 수치가 있다. 압축(meshopt 89.2% 절감)이 이 한도를 9배 늘려주는 것도 같은 축의 이야기다.

05기각한 논거와 남은 한계

✗ 스로틀 회피 — 실험으로 기각

AWS t3 계열은 네트워크가 버스터블이고 크레딧이 마르면 조용히 스로틀된다. 부팅 이후 누적 bw_in_allowance_exceeded 가 11 이었으므로 실제로 발동한 이력이 있다. 인과를 확정하려고 32.9MB IFC 를 10회 연속(총 329MB, 평균 72.3 Mbps) 밀어 봤으나 카운터 0 증가였다. 집 상향 72 Mbps 로는 t3.medium 의 inbound 임계에 닿지 않는다. 누적 11건은 다른 활동에서 나온 것이고, 소비자 회선으로는 이 논거를 세울 수 없다. egress 쪽 bw_out 은 20.16GB 를 서빙해도 0 이었다.

서버 상한은 하한 근사다 — §03 의 핵심 근거가 미검증

loopback 은 C=1 로만 잰다. 2 vCPU(AWS)에서 부하 생성기와 서버가 CPU 를 나눠 쓰므로 실제 상한은 더 높다. §03 의 참가자당 속도표는 이 상한을 인원으로 나눈 산출값 이며, 실제로 여러 클라이언트가 동시에 받을 때 2배 비율이 유지되는지는 확인하지 않았다. AWS 는 2 vCPU 라 부하가 커질 때 KOREN 보다 더 빨리 무너질 수도 있어, 실측하면 격차가 커질 가능성도 있다.

전송 계층이 다르다 (계획서 §4-3)

AWS 는 https → nginx → proxy_pass → uvicorn, KOREN 은 http → uvicorn 직결이다. KOREN 이 TLS 핸드셰이크 14.75 ms 를 내지 않는다 (핸드셰이크 총합 AWS 25.0 ms vs KOREN 11.4 ms). 처리량 비교에는 영향이 미미하나(raw 8초에 0.19%) TTFB 비교는 오염된다. KOREN 에 nginx + TLS 를 붙이는 것이 정석이다.

집에서 KOREN 을 재는 것은 목적과 다르다

경로가 집 → LG U+ → 피어링 → KOREN 이다. KOREN 의 망 이점은 클라이언트도 KOREN 에 있을 때 나온다. §02 의 "KOREN 이 약간 느리다" 를 "KOREN 이 나쁘다" 로 읽어서는 안 된다 — 소비자 ISP 에서 연구망으로 들어가는 경로가 AWS 서울 피어링보다 불리하다는 뜻이다. 서버 RTT 는 KOREN 13.8~16.8 ms, TCP 연결은 KOREN 8.59 ms vs AWS 5.25 ms 다.

Wi-Fi 노이즈 · 단일 지점

전 세션이 가정 Wi-Fi 1지점이다. 공유기 RTT mdev 는 세션에 따라 2.88~21.83 ms 로 흔들렸다. 유선으로 재면 CV 가 낮아진다.

06다음 실험 — 다중 클라이언트 상한 실측

§03 의 "10인 방에서 2배" 는 이 보고서에서 유일하게 KOREN 을 정당화하는 성능 수치인데 아직 산출값이다. 실측으로 바꾸는 방법은 클라이언트를 여러 대 두는 것이다. KOREN VM 에 SSH 가 있으므로 지금 가능하다.

  1. KOREN VM 을 AWS 의 클라이언트로 쓴다. KOREN 은 1 Gbps 급 연구망이므로 집 회선(300 Mbps)보다 훨씬 큰 부하를 걸 수 있다. AWS 서버가 몇 Mbps 에서 무너지는지 단독으로 확인한다 (C=1,3,10 스윕).
  2. 반대로 AWS 쪽에서 KOREN 을 때린다. AWS SSH 가 없으므로 서버 담당자에게 요청하거나, 집 노트북 + KOREN VM 두 대를 동시에 AWS 로 향하게 해 합계 상한을 본다.
  3. 합계가 loopback 상한에 수렴하는지 본다. 수렴하면 §03 표가 실측으로 뒷받침된다. 미달하면 상한이 더 낮다는 뜻이고 §03 을 하향 수정해야 한다.
  4. 같은 실험을 KOREN 서버에도 한다. 두 서버의 다중 클라이언트 상한 비율이 loopback 비율(2.01배)과 같은지 확인한다.

egress 주의: AWS 를 대상으로 하는 부하는 전부 egress 과금 대상이다. 이미 20.16GB 를 썼고 무료 한도는 100GB 다. C=10 스윕은 meshopt 기준 세션당 약 8GB 이므로 남은 예산 안에서 2~3회가 한계다. KOREN 대상 부하는 과금이 없다.
