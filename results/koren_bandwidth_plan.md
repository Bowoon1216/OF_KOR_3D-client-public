# KOREN vs 일반망 — 한 노트북·한 IP 로 차이를 드러내는 실험 계획

## 0. 문제 정의

**단일 사용자 다운로드로는 KOREN 과 일반망의 차이가 안 나온다.** 이건 예상이 아니라 이미
측정됐다 — [`transfer_run_journal.md`](transfer_run_journal.md) §3.1 에서 AWS 단일 스트림이
341.38 Mbps 였고, 집 회선 speedtest 는 ↓276.12 Mbps (`logs/00_speedtest.txt`) 다.
**병목이 우리 집 회선이므로, 서버가 무엇이든 같은 값이 나온다.**

차이가 날 상황은 **여러 명이 동시에 올리고 받을 때**다. 이 문서는 그 조건을
**한 노트북·한 IP** 로 만들어, **무엇을 볼 수 있고 무엇을 원리적으로 못 보는지** 가른다.

### 제약 (전제로 고정)

- 실험은 **노트북 1대, IP 1개**에서 한다. 여러 사람이 여러 회선에서 동시에 붙는 구성은 쓰지
  않는다 (일정 조율 문제가 아니라 실험 조건이다)
- 대상 파일은 §4-2 가 동결한 `site_stacked_*.glb` 3종. 재생성 금지
- 하네스는 `scripts/measure.py` (전송) 와 `tools.loadgen` (동기화). 새로 만들지 않는다

### IP 개수는 이 실험의 제약이 아니다

방화벽 규칙은 `(출발지 IP, 목적지 IP, 포트)` 단위고 **한 IP 에서 맺는 연결 수를 제한하지
않는다.** 노트북 한 대에서 동시 세션 6개를 열어도 규칙 하나로 통과한다 — `measure.py` 의 C=10
조건이 이미 그렇게 돌았다. **6인 팬아웃에 6개 IP 가 필요하지 않다.**

## 1. 먼저 인정해야 하는 한계 — 동시성을 올려도 서버 쪽 경합은 재현되지 않는다

§3.1 의 동시성 스윕이 이걸 이미 측정했다.

| 조건 | 스트림당 | 합계 |
|---|---:|---:|
| meshopt C=1 | 304.63 Mbps | 305 Mbps |
| meshopt C=3 | 115.12 Mbps | 345 Mbps |
| meshopt C=10 | 39.33 Mbps | **393 Mbps** |
| draco C=10 | 37.15 Mbps | 372 Mbps |

**스트림당 처리량이 동시성에 정확히 반비례하고 합계는 평탄하다.** 고정된 파이프를 나눠 쓰는
형태다. 따라서 한 노트북에서 세션을 6개, 10개로 늘려도 **서버에 걸리는 총 요구량은 회선
상한(~350–400 Mbps)을 넘지 못한다.**

| 질문 | 이 조건에서 답할 수 있나 |
|---|---|
| KOREN 이 일반망보다 **총 대역이 큰가** | **못 한다.** 우위는 회선 상한 위쪽에 있고, 우리 요구량이 거기 못 닿는다 |
| KOREN 이 일반망보다 **못하지 않은가** | **된다.** KOREN 경로 용량이 회선 상한보다 낮으면 곡선이 더 낮은 지점에서 포화한다 |
| 동시 부하 상황에서 **사용자 체감이 어떻게 무너지는가** | **된다. 이게 §2 의 주 실험이다** |

"6명 동시" 를 한 노트북으로 흉내 내는 것 자체는 정당하다 (연결 수 제한이 없으므로). 다만
**그것으로 대역 우위를 증명할 수는 없다.** 지표를 처리량에서 **경합 하의 지연**으로 바꿔야
한 노트북에서 차이가 드러난다.

## 2. 주 실험 — 회선을 채운 상태에서 동기화 지연이 얼마나 무너지는가

### 왜 여기서 차이가 나는가

큐잉 지연과 버퍼블로트는 **회선 상한 아래에서도** 경로 구성에 따라 크게 갈린다. 벌크 전송이
경로 버퍼를 채우면 같은 경로를 타는 실시간 패킷이 그 큐 뒤에 줄을 선다. 총 대역이 같아도
**버퍼 정책·혼잡 제어·경로 홉 수가 다르면 지연 열화 폭이 다르다.** speedtest ping 이 56.82 ms
인 경로라면 이 효과가 작지 않다.

그리고 이게 제품 주장과 직결된다: **협업 중 누가 에셋을 받는 동안 제스처 동기화가 버티는가.**

### 설계

한 노트북에서 두 하네스를 동시에 돌린다. 조건 4개를 각 경로(AWS / KOREN)마다 잰다.

| 조건 | 전송 부하 | 재는 것 |
|---|---|---|
| L0 | 없음 | 동기화 지연 기준선 |
| L1 | 다운로드 C=1 | |
| L3 | 다운로드 C=3 | |
| L6 | 다운로드 C=6 | 회선 포화 상태 |

**판정은 절대값이 아니라 Δ(L6 − L0)로 한다.** 이유는 §3 참조.

| 지표 | KOREN L0 (기측정, loopback) | 기록 |
|---|---:|---|
| e2e p50 | 0.90 ms | |
| e2e p95 | 1.38 ms | |
| e2e p99 | 1.57 ms | |
| 100ms 초과 비율 | 0.00% | |

**1차 판정 지표는 `100ms 초과 비율`과 `e2e p99`다.** 두 경로에서 Δ 를 비교한다.

### 실행

```bash
# 터미널 1 — 동기화 하네스를 먼저 띄워 기준선 30초를 확보한 뒤 부하를 건다
python -m tools.loadgen --clients 6 --rate 30 --duration 180 \
  --run-id 2026-09-XX_home_load_koren_L6      # 원격 타겟 지정 플래그는 §6-1 확인 필요

# 터미널 2 — 30초 뒤 전송 부하 투입
sleep 30
.venv/bin/python scripts/measure.py --target <url> --label koren_load \
  --download meshopt:6:10 --location home --network-type wifi
```

`--duration 180` 안에 무부하 30초 + 부하 구간이 함께 들어가므로, **한 실행 안에서 전후를
비교**할 수 있다. loadgen 이 구간별 집계를 못 내면 L0 과 L6 을 별도 실행으로 나눈다.

**노트북 CPU 를 확인한다.** loadgen 하네스 CPU 는 KOREN loopback 에서 2.3% 였다. 여기에
curl 프로세스 6개가 붙으므로, 하네스 CPU 가 크게 오르면 지연 열화의 원인이 경로가 아니라
**내 노트북**이 된다. 그러면 그 세션은 못 쓴다.

## 3. 원격 측정에서 e2e 절대값을 믿지 않는다

KOREN 기준선은 **서버 내부 loopback** 에서 나온 값이라 시계 보정 불확실도가 0.28 ms 였다.
클라이언트에서 재면 왕복이 56 ms 규모이므로 **이 불확실도가 수 ms~수십 ms 로 커진다.**
e2e 가 1 ms 대인 값과 직접 비교할 수 없다.

그래서:

- **경로 간 비교는 Δ(부하 − 무부하)로 한다.** 시계 오차는 두 구간에 공통으로 들어가므로 차분에서
  상쇄된다
- loadgen 이 출력하는 **`RTT` 와 `시계 보정 불확실도`를 매 실행 기록한다.** 불확실도보다 작은
  차이는 "차이 없음" 으로 쓴다
- `100ms 초과 비율`은 시계 오차에 상대적으로 둔감하므로 1차 지표로 쓰기에 적합하다

## 4. 보조 실험 (같은 세션에서 공짜로 나온다)

### 4-1. 스트림당 분포 — 합계가 아니라 분산을 본다

동시 6스트림에서 **스트림당 완료시간 p95/p50 과 CV**. 합계가 회선에 막혀 같아도, 경로가
스트림을 어떻게 나누는지는 다를 수 있다. `report.py` 표 1 이 이미 p50·p95·CV 를 낸다.

C=10 에서 AWS 의 CV 는 0.415 였다 (C=1 은 0.106). **같은 C 에서 CV 가 낮은 경로가
사용자에게 더 균일하다.**

### 4-2. RTT·지터 — 동시 부하 없이도 보인다

집 회선 speedtest ping 56.82 ms 는 큰 값이고, AWS 는 ICMP 를 막아 서버 RTT 를 못 냈다
(§3.5, 30발 전손실). **KOREN 이 ICMP 를 열어 두면 `measure.py` 진단이 자동으로 수집한다** —
`--skip-probes` 를 넣지 않는다. 여기서 유리하면 그것만으로도 발표 근거가 된다.

Wi-Fi 노이즈 바닥값(§3.5: 공유기 mdev 11.61 ms, 최대 80.24 ms)이 이 모든 값에 포함된다.
**유선으로 붙을 수 있으면 붙는다** — 같은 노트북·같은 IP 를 유지하면서 노이즈를 줄이는
유일한 수단이다.

### 4-3. 업로드는 이미 닫혔다

§3.2: hoist 69.60 Mbps ≈ speedtest 상향 65.66~71.39 Mbps, 서버 작업(`store+db`)은 **3.0%**.
**가정 회선 비대칭 때문에 우리 집이 병목인 것이 실측으로 확인됐다.** 동시 업로드를 6개 걸면
상향 71 Mbps 를 6이 나눠 쓸 뿐이다. 업로드는 KOREN 대역 평가용이 아니라 "실사용자 업로드
소요 시간" 주장에만 쓴다.

## 5. 하네스는 `measure.py` 를 쓴다 — 셸 루프를 쓰지 않는 이유

동시 세션을 만들 때 `for i in $(seq 1 6); do curl … & done; wait` 를 쓰면 네 가지가 기존
데이터와 어긋나서, 나온 값을 §3.1 표와 같은 표에 넣을 수 없다.

| 문제 | 결과 | `measure.py` 는 |
|---|---|---|
| **배리어가 없다** | 프로세스 생성 지연만큼 스트림이 계단식으로 시작한다 — C=6 을 재는 게 아니다 (§5.1) | `threading.Barrier` 로 발사 시점을 맞춘다 |
| **워밍업을 안 버린다** | 첫 라운드의 slow-start 가 섞인다 (§4-4) | 조건마다 1라운드 폐기 |
| **대상 URL 을 손으로 적게 된다** | 동결 파일이 아닌 것을 재면 AWS 값과 비교 불가 | `download_targets_*.json` 에서 URL·크기·sha256 을 읽는다 |
| **스키마가 없다** | `report.py`·`check_schema.py` 가 못 먹는다 | §7 스키마로 JSON 출력 |

동시성은 플래그로 그대로 표현된다 — 별도 도구가 필요 없다.

```bash
--download meshopt:1:30 meshopt:3:20 meshopt:6:20 meshopt:10:20
```

`--label koren` 이면 기본 매트릭스(raw C=1, meshopt C=1/3/10, draco C=1/10)가 돌아
**AWS 세션과 조건이 1:1 로 맞는다.**

## 6. 측정 전에 해결해야 하는 것

### 6-1. loadgen 을 클라이언트에서 원격 서버로 붙일 수 있는가 — **주 실험의 전제**

KOREN 기준선은 서버 내부에서 돌았다. §2 는 **노트북에서** 붙어야 성립한다. 타겟 지정 플래그가
없으면 주 실험을 할 수 없다.

```bash
python -m tools.loadgen --help     # 먼저 이걸 찍고 출력을 로그로 남긴다
```

없으면 서버 담당자에게 요청한다. 프론트엔드는 `VITE_WS_BASE_URL` 로 원격 wss 에 붙고 있으므로
(`.env.local`) 서버 쪽 제약은 아니다.

### 6-2. 경로 구성이 다르다

붙여받은 KOREN 주소는 `http://…:8000` (평문·uvicorn 직결)이고 AWS 기준선은 `https://…` +
nginx 1.24.0 이다 (§2 응답 헤더). 이대로면 차이가 나도 **회선 때문인지 TLS·nginx 부재
때문인지 갈라낼 수 없다.** TLS 핸드셰이크는 §3.3 에서 CLI TTFB 34.4 ms 중 25.0 ms(72%)를
차지한 실측 항목이다.

지연 비교에서는 이게 처리량 비교보다 더 중요하다. **선택지 3개 중 하나를 측정 전에 고른다:**

1. **KOREN 에도 nginx + TLS** — 가장 깨끗하다. 인증서는 nip.io 방식으로 동일하게 갈 수 있다
2. **AWS 를 평문 8000 으로도 한 번 더 잰다** — 대조군을 KOREN 에 맞춘다. egress 를 다시 태운다
3. **차이를 기록하고 진행** — 최후 수단. 결론에 "경로 구성이 다름" 을 항상 병기하고, 개선폭을
   단독 수치로 발표하지 않는다

### 6-3. 대상 배치 — KOREN 에 동결 파일을 올린다 (1회)

```bash
.venv/bin/python scripts/publish.py --target <koren-url> --label koren \
    --email <이메일> --password-file <경로>
```

`publish.py` 는 올린 뒤 **서버가 돌려준 sha256 을 로컬과 대조**하고 `results/download_targets_koren.json`
을 만든다. AWS 에서 3개 파일 모두 일치했다 (§2). **KOREN 에서도 같은 바이트를 쟀다는 근거가
이렇게 남는다** — §4-2 가 요구하는 것이 이것이다.

비밀번호는 `--password-file` 로만 넘긴다. 명령줄 인자로 주면 세션 메타의 `command` 필드에 그대로
적혀 `results/` 에 커밋된다.

### 6-4. 사전 기록 (없으면 곡선을 해석할 수 없다)

```bash
# 측정에 쓸 회선 — 노트북에서
speedtest --simple                  # 또는 speedtest.net 캡처

# KOREN 서버 제원 — sync_latency_aws_plan.md §4 캡처와 같은 명령
nproc; free -h; df -h; uname -a
python3 -V; pip show uvicorn fastapi | grep -E 'Name|Version'
# 서빙 매체 — 마운트 목록으로 끝내지 말 것. AWS 에서 이걸로 두 번 틀렸다 (journal §0)
df -h | grep -i tmp                 # 마운트가 있는가
# 측정 경로가 그 마운트인가 → nginx/백엔드 접근 로그에서 실제 요청 경로를 확인한다
```

`measure.py` 는 세션 진단으로 speedtest·ping·traceroute 를 자동 수집한다. **`--skip-probes` 를
넣지 않는다** — §4-2 의 RTT·지터 비교가 여기서 나온다.

### 6-5. 집계

```bash
.venv/bin/python scripts/report.py \
    results/transfer_*_commercial.json \
    results/transfer_*_koren.json \
    results/transfer_*_loopback.json
.venv/bin/python scripts/check_schema.py results/transfer_*.json
```

`label` 별로 행이 갈리고, loopback 파일이 함께 있으면 `loopback 상한 대비` 비율까지 나온다.

### 6-6. NOC 문의 (우선순위 낮음)

등록 가능한 IP 3개가 **정책 상한이 아니라 신청한 개수**일 수 있다. 기관 회선이면 `/24` 같은 대역
단위 등록이 가능한지 물어볼 가치는 있다. 다만 이 문서의 실험은 IP 1개로 설계되어 있으므로
**막혀도 계획은 그대로 진행된다.** 나중에 §1 이 못 낸다고 적은 "총 대역 우위" 를 재려면 이 문의가
필요해진다 — 그때를 위해 남겨 둔다.

## 7. egress·비용

| 세션 | 크기 |
|---|---:|
| AWS 기본 매트릭스 (기측정) | **17.14 GB** |
| KOREN 기본 매트릭스 | 약 17 GB (KOREN 과금 여부 **확인 필요**) |
| §2 부하 조건 4개 (meshopt C=1/3/6 × R=10) | 약 4 GB |

`measure.py` 는 egress 예상치를 먼저 출력하고 **60 GB 를 넘으면 `--yes` 없이 중단한다**(§11).
AWS 쪽 측정에는 ENA 스로틀 감시가 켜져 있어야 한다 — 고동시성 다운로드는 실제로
`bw_out_allowance_exceeded` 를 올릴 수 있고 그 라운드는 집계에서 빠져야 한다. KOREN 에 같은
엔드포인트가 없으면 감시 없이 돌리고 `throttle watch: off` 를 기록한다.

## 8. 판정 규칙 (숫자를 보기 전에 정한다)

| 관측 | 해석 |
|---|---|
| Δ(100ms 초과 비율)이 KOREN 에서 뚜렷이 작다 | **주 결론.** 동시 부하 상황에서 KOREN 이 실시간성을 지킨다 |
| Δ 가 두 경로에서 비슷하다 | 이 조건에서는 차이 없음. **회선이 천장이라 못 봤을 가능성**을 함께 적는다 (§1) |
| KOREN 합계 처리량이 회선 실측보다 낮은 지점에서 포화 | 그 값이 KOREN 경로 상한이다 — 유일하게 대역을 직접 잡는 경우 |
| 같은 C 에서 CV 가 한쪽이 낮다 | 스트림 간 균일성 우위 (보조 근거) |

**금지 사항 3개:**

- **"KOREN 이 총 대역에서 우수하다" 를 이 데이터로 주장하는 것.** §1 이 원리적으로 그걸 못
  낸다고 적었다. 필요하면 회선 상한을 넘는 요구량을 만들 수 있는 환경(다중 회선·기관 유선)이
  따로 필요하다
- 경로 구성이 다른 상태(§6-2 선택지 3)에서 개선폭을 단독 수치로 내는 것
- 시계 보정 불확실도보다 작은 e2e 차이를 개선으로 쓰는 것 (§3)

## 9. 미확정 (추측으로 채우지 않는다)

| # | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | `tools.loadgen` 이 원격 타겟을 받는지 | **§2 주 실험의 전제.** 없으면 실험 불가 |
| 2 | loadgen 이 구간별(부하 전/후) 집계를 낼 수 있는지 | 못 내면 L0·L6 을 별도 실행으로 쪼갠다 |
| 3 | KOREN 접속 주소·포트·nginx/TLS 유무 | §6-2 선택. `KOREN_IP_REDACTED:8000` 은 레포에 근거가 없다 |
| 4 | KOREN 에 `publish.py` 가 쓸 계정이 있는지 | 없으면 동결 파일을 올릴 수 없다 |
| 5 | KOREN 의 **측정 경로**와 그 매체 | journal §0 에서 두 번 틀린 항목. 마운트 존재가 아니라 **접근 로그의 실제 요청 경로**로 확정하고, `--serving` 에 그 값을 넘긴다. AWS 는 `a_*`(EBS)였으므로 KOREN 도 EBS 면 매체가 맞아 비교가 성립한다 |
| 6 | KOREN 이 ICMP 를 여는지 | 열려 있으면 AWS 에서 못 낸 서버 RTT 를 얻는다 (§4-2) |
| 7 | KOREN 에 `net-allowance` 상당이 있는지 | 없으면 스로틀 감시 없이 돌린다 (§7) |
| 8 | 측정 노트북을 유선으로 붙일 수 있는지 | Wi-Fi mdev 11.61 ms 노이즈를 줄이는 유일한 수단 (§4-2) |

서로의 부하가 되므로 따로 돌린다** — 단, §2 의 "전송 + 동기화 동시" 는 의도된 예외다.
