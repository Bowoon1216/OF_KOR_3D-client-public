## loopback 세션 판정과 기록 (2026-08-14)

### §11 판정 — 통과

`loopback / commercial` = **raw 4.97배 · meshopt 4.52배 · draco 3.86배.** 세 변형 모두 3배를
넘으므로 §11 의 보고 기준에 걸리지 않는다. journal §3.1 이 간접 근거(동시성 무관 합계 포화)로
내렸던 **"서버는 병목이 아니다" 가 직접 증거로 확인됐다.**

서버 상한은 **1.02~1.70 Gbps** 다. 집 회선 실측(↓276 Mbps)의 약 4~6배이므로, 회선이 개선되면
서버가 받아줄 여유가 그만큼 있다 — 9월 KOREN 측정의 헤드룸 근거다.

작은 파일일수록 비율이 낮다 (raw 4.97 → draco 3.86). 고정 비용이 전송 시간에서 차지하는 비중이
커지기 때문이다: loopback draco 는 elapsed 107.8 ms 중 TTFB 35.0 ms = **32%** 가 고정 비용이다.

### 고정 비용은 네트워크가 아니라 CPU 다 (§3.3 정정)

| | commercial | loopback |
|---|---:|---:|
| TTFB p50 | 34.4 ms | **35.05 ms** |
| 핸드셰이크(`connect`) p50 | 25.0 ms | **33.54 ms** |

**네트워크를 완전히 제거해도 핸드셰이크가 줄지 않는다 — 오히려 늘었다.** journal §3.3 은 이
25 ms 를 "연결 수립 비용" 으로만 적었는데, 그 정체는 전파 지연이 아니라 **TLS 연산과 curl 프로세스
기동의 CPU 시간**이다. loopback 값이 더 큰 것은 2 vCPU 에서 curl 과 서버가 CPU 를 다투기
때문으로 보이며(클라이언트가 i9 맥북이었던 commercial 과 조건이 다르다), 이 차이의 정체는
측정으로 확정하지 않았다.

실무적 함의: **회선이 개선돼도 이 고정 비용은 남는다.** 작은 파일에서 KOREN 개선폭을 크기
비례로 기대하면 안 된다.

### 이 세션의 메타데이터에 대해 (§8.3 필수 명시)

1. **`--serving` 을 `ebs gp3 (/static/assets/a_*, …)` 로 넘겼다** — 상용 기준선이 실제로 때린
   경로가 EBS `a_*` 였다(nginx 접근 로그). tmpfs `bench/` 는 측정 경로가 아니었다. 저장 매체가
   다른 두 값으로 비율을 내면 이 판정이 오염된다. 8/13 세션 JSON 3개도 같은 이유로 정정했다
2. **`--skip-probes` 를 켰다** — loopback 에는 잴 회선·RTT·경로가 없다. 이 플래그가 남기는
   `"하네스 검증용. 실제 세션에서는 쓰지 말 것"` note 와, 위 §11 목록의
   `"ping 을 실행할 수 없는 하네스"` 문구는 **이 세션에 대해 부정확하다.** 하네스가 못 하는 게
   아니라 잴 대상이 없어서 끈 것이다
3. **`--location other --network-type wired` 는 무의미하다** — loopback 에는 위치도 회선도 없다.
   `--location` 선택지에 해당 값이 없어 `other` 를 썼다
4. **이 값은 "상한" 이 아니라 "상한의 하한 근사"** 다 — 2 vCPU 에서 curl 과 서버가 CPU 를 나눠
   쓴다(`measure.py` 가 loopback 을 C=1 로 강제하는 이유). 실제 서버 상한은 이보다 높다
5. 정적 서빙 주체는 nginx 가 아니라 백엔드 FastAPI `StaticFiles` 이고 nginx 는 `proxy_pass` 만
   한다. 이 값을 "nginx 상한" 으로 부르지 않는다
