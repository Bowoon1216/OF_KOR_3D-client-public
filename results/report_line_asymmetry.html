회선 용량에 도달했다는 근거

동시성을 1 → 3 → 10 으로 10배 올려도 합계 처리량이 341 → 345 → 393 Mbps 에서 멈춘다. 스트림당 처리량이 동시성에 거의 정확히 반비례한다 (304.63 → 115.12 → 39.33). 고정된 용량을 나눠 쓰는 형태이며, 서버가 여유가 없어서 나는 현상이 아니다.

단일 스트림 341.38 Mbps 는 같은 세션의 speedtest 실측(227.12 Mbps)의 150% 다. speedtest 가 회선을 과소평가했고, 실제 용량은 340~390 Mbps 대에 있다.

서버 상한은 회선의 4~5배 — loopback 직접 측정

위 논거는 간접 근거다. 서버가 자기 자신을 부르게 해(loopback) 네트워크를 뺀 상한을 직접 쟀다. 같은 공개 호스트명·같은 TLS·같은 nginx 블록을 타되 주소만 127.0.0.1 로 꺾었고, ENA 스로틀 카운터가 움직이지 않아 트래픽이 ENI 를 거치지 않았음을 확인했다.

서버 상한은 1.02~1.70 Gbps 로 집 회선의 4~6배다. 세 변형 모두 계획서가 정한 보고 기준(3배)을 넘으므로, “서버가 병목이 아니다” 는 간접 근거가 직접 증거로 확인됐다. 작은 파일일수록 배수가 낮아지는 것(4.97 → 3.86)은 고정 비용 비중이 커지기 때문이다.

이 값은 “상한” 이 아니라 “상한의 하한 근사” 다. 2 vCPU 에서 부하 생성기와 서버가 CPU 를 나눠 쓰므로(그래서 loopback 은 C=1 로만 잰다) 실제 상한은 더 높다. 정적 파일을 내는 것은 nginx 가 아니라 FastAPI StaticFiles 이므로 “nginx 상한” 이라고 부르지 않는다 — uvicorn + ASGI 미들웨어 + 프록시의 합이다.

서버 처리 시간은 3% 다

recv 95.5%
recv 본문 수신 · 3,602.7 ms — 네트워크 시간 store + db 서버 작업 · 114.4 ms 나머지 · 56.6 ms

recv 는 서버 처리 시간이 아니다. nginx 가 proxy_request_buffering off 로 본문을 흘려보내므로 서버의 multipart 파싱이 클라이언트 바이트 도착 속도에 묶인다. 따라서 서버가 실제로 일한 시간은 store + db 뿐이고, 네트워크 시간은 3,773.7 − 114.4 = 3,659.3 ms 다.

recv 를 추가로 빼면 네트워크 시간이 56.6 ms — 실제의 1.5% — 로 나와 회선 성능을 65배 좋게 잡는다. 9월 KOREN 비교에서 이 이중 차감을 하면 개선폭을 과소평가한다.

CLI TTFB 34.4 ms 중 25.0 ms(72%)가 연결 수립 비용이고 서버가 응답을 시작하는 데 쓰는 시간은 8~9 ms 다. 브라우저가 커넥션을 재사용한 상태에서 독립적으로 측정한 순수 서버 응답 8.1 ms 가 CLI 의 잔차와 일치한다 — 두 하네스가 서버 구간에서 교차 검증됐다. 마지막 약 60 ms 는 slow-start 로 해석되나 측정으로 확인한 것이 아니라 추정이다.

실무적 의미: 파일당 약 95 ms 의 고정 비용이 붙으므로, 작은 파일을 여러 번 받는 것보다 한 번에 받는 것이 유리하다.

06이 수치를 인용할 때 함께 밝힐 것

Wi-Fi 노이즈가 포함되어 있다

공유기까지의 RTT 가 avg 7.243 ms / mdev 11.61 ms / 최대 80.24 ms (손실 0%) 였다. mdev 가 avg 보다 크다는 것은 간헐적 스파이크가 있다는 뜻이며, 이 노이즈가 위 모든 측정값에 들어 있다. 유선으로 재면 CV 가 낮아질 것이다.

서버 RTT 를 ping 으로 측정하지 못했다

AWS 가 ICMP 를 차단해 30발 전부 손실됐다. traceroute 도 9홉까지만 응답하고 목적지에 도달하지 못했다. 대용으로 다운로드 TTFB 중앙값 39.2 ms 를 기재했다 — 왕복 1회와 서버 응답 시작을 포함하므로 RTT 의 상한 근사다.

서버 상한은 하한 근사다

loopback 으로 1.02~1.70 Gbps 를 실측했지만, 2 vCPU 에서 부하 생성기와 서버가 CPU 를 나눠 쓰므로 이 값은 상한의 하한 근사다. 실제 상한은 더 높다. 회선이 10 Gbps 급으로 바뀌면 이 값으로는 서버가 받아줄지 판단할 수 없고, 별도 부하 생성기를 둔 측정이 필요하다.

tmpfs 가 아니라 EBS 에서 서빙됐다

계획서는 tmpfs 서빙을 전제하지만, 측정이 실제로 때린 경로는 /static/assets/a_* (EBS gp3) 였다 — 서버 nginx 접근 로그로 확인했다. 이 조건에서도 회선 용량을 다 채웠으므로 결론은 바뀌지 않는다. 정적 파일을 내는 것은 nginx 가 아니라 FastAPI StaticFiles 이며 nginx 는 proxy_pass 만 한다.

단일 지점 · 단일 시각이다

가정 Wi-Fi, 자정 무렵 1회 측정이다. 시간대·위치를 바꾸면 값이 달라진다. 8월 측정의 목적은 도구 검증과 수치 감각 확보이며, 발표용 비교 데이터는 9월에 같은 장소·같은 기기·같은 시간에 AWS 와 KOREN 을 동시 측정해 얻는다.

업로드 p95 와 동시성 스윕이 없다

R=20 이라 표본이 30 미만이어서 p95 를 산출하지 않았다. 업로드 동시성도 재지 않았다 — 가정용 상향 대역이 낮아 C 를 올리면 회선만 포화되기 때문이다. 업로드 합계도 70 Mbps 대에서 포화할 것으로 보이나 이는 측정하지 않은 추정이다.

비교 시 반드시 지킬 것

  1. 같은 파일을 쓴다. 씬을 재생성하지 않는다. 세 파일의 sha256 이 기록되어 있다.
  2. recv 를 빼지 않는다. 서버 작업은 store + db 뿐이다.
  3. KOREN 처리량을 서버 상한과 대조한다. 서버 상한은 1.02~1.70 Gbps 로 실측됐다. KOREN 측정치가 이 구간에 근접하면 회선이 아니라 서버에 걸린 것이므로 개선폭이 과소평가된다 — 그때는 loopback 을 다시 재고 부하 생성기를 분리한다.
  4. loopback 도 같은 a_* 경로를 잰다. 매체가 다른 두 값으로 비율을 내면 3배 판정이 오염된다.
  5. 스로틀 카운터를 대조한다. t3 계열은 네트워크가 버스터블이며, 크레딧이 마른 구간의 측정값은 회선이 아니라 AWS 정책을 잰 것이다.
